LAB4 environment (2026-10-13/14), same WSL2 Ubuntu 20.04.6 + ROS Noetic host as LAB3
- Code: VNAV2023 lab4 packages + dependencies (mav_trajectory_generation, nlopt, glog, yaml-cpp, eigen
  wrappers, mav_comm) built in ~/vnav_ws with catkin build (20 packages). The lab3 copies of
  catkin_simple and mav_comm were removed to avoid duplicate packages.
- Simulator: vnav.mit.edu/material/lab4.zip (Unity 2019.3.9f1). Under WSLg it aborts while creating the
  GL context ("[xcb] Unknown sequence number ... XInitThreads has not been called") unless started with
  single-threaded rendering:  ./lab4.x86_64 -force-gfx-direct -screen-fullscreen 0 -screen-width 1024
  -screen-height 768  (renders on the RTX 4070 SUPER through D3D12; ~50-70 fps).
- Bridge: roslaunch tesse_ros_bridge tesse_quadrotor_bridge.launch publish_collisions:=true
  The lab4 build restarts its clock on the start-up scene change, which tripped
  assert(prev_time < metadata['time']) in tesse_ros_node.py and killed the metadata thread
  (no /current_state). Local patch (scripts/patch_bridge.py): resync prev_time instead of asserting.
- Gates: 12 objects red_square_drone_door (0..11) in vnav-2020-lab4_static_tfs.csv; each is a sprite with
  no collider (flying through gate 0 at lateral offsets 0-2.5 m produced no collision messages), and the
  size is not in the data. Pass criterion used throughout: drone centre within 0.6 m of the gate centre,
  gates in order (scripts/race_check.py). Race time: first /desired_state -> first entry into the 0.6 m
  ball of gate 11.
- Respawn: R sent to the Unity window with xdotool; the simulator keeps applying the last rotor command,
  so a zero command is published first (scripts/run_race.sh).
- Collisions: every take-off reports 1-3 Floor_01 contacts at the instant the drone leaves the floor;
  no other collisions in the successful runs.
- Correction (2026-10-16): -force-gfx-direct alone does not prevent that abort. On 2026-10-16, 13 of 18
  starts with it still crashed, ~1.5 s after the window appears, in IsRendererSupported, i.e. while Unity
  probes which OpenGL version it can use (an XInitThreads() LD_PRELOAD shim made no difference).
  Asking for the 3.3 core profile it ends up with, -force-glcore33, gave 9 of 9 clean starts with the
  same renderer (D3D12, OpenGL 3.3 Core, Mesa 21.2.6) and the same race result (12/12, 6.76 s).
  Separately, WSLg once left a new simulator window hidden on the Windows desktop (RAIL window without
  WS_VISIBLE while X reported it mapped); unmapping and mapping the X window again shows it (race.sh does
  this on every run).
